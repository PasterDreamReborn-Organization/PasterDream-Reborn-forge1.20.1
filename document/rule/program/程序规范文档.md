# 程序规范

## Git 管理

### 仓库

- **单加载器 + 单 Minecraft 版本**：本仓库仅对应 Forge 加载器与 Minecraft 1.20.1，不涉及多加载器或多版本兼容

### 分支

- **主分支**：`master` 分支，始终保持与最新开发进度同步
- **开发者个人分支**：命名为 `dev-<开发者姓名>`（如 `dev-shiliuyinyu`）

### 提交

**Commit message 格式**：`[type](scope): message`

| type     | 说明                         |
| -------- | ---------------------------- |
| feat     | 新增玩法/功能                |
| fix      | 修复逻辑/表现 bug            |
| docs     | 仅文档变更                   |
| style    | 代码样式调整（无运行影响）   |
| refactor | 重构/代码清理                |
| perf     | 性能优化                     |
| test     | 添加或修改测试               |
| chore    | 更新工具/辅助脚本/杂项       |
| art      | 替换/更新美术资源            |
| asset    | 更新数据表/配置              |

**示例**：

- `feat(block): 添加锻造工坊多方块结构`
- `fix(entity): 修复梦魇实体 AI 目标选择异常 (Fixes #42)`
- `refactor(network): 重构数据包同步逻辑`
- `docs(readme): 更新安装说明`
- `chore(build): 添加 Curios API 依赖`

> 单个 Commit message 可以带多个 `[type](scope): message` 格式的消息。

## 代码风格 & 命名规范

- **命名体系**：严格遵循 Java 驼峰命名规范
- **类名**：大驼峰（PascalCase），如：`DreamCauldronBlock`
- **方法名**：小驼峰（camelCase），如：`getDreamEnergy()`
- **常量**：全大写 + 下划线分隔，如：`MAX_DREAM_ENERGY`
- **包名**：全部小写，单词间直接连接，不使用驼峰或蛇形（如 `com.pasterdream.block` 而非 `com.pasterDream.Block` 或 `com.paster_dream.block`）。`NOT_MODIFY` 目录例外，可使用大写
- **特殊规则**：
    - **复数限制**：仅允许用于集合/列表类变量（如 `items`、`blockTags`），普通变量或类名禁止使用复数
    - **数据生成器后缀**：所有数据生成类须以 `Provider` 结尾，如 `ModBlockLootTablesProvider`
    - **注册中心类前缀**：以 `Mod` 为前缀，如 `ModItems`、`ModBlocks`
    - **方块实体类后缀**：以 `BlockEntity` 为后缀，如 `DreamCauldronBlockEntity`

## 易犯错误记录

### 官方映射下前置模组 Mixin 兼容问题

当使用 `official`（Mojang）映射渠道时，部分第三方模组（如 Curios、GeckoLib）的 `refmap.json` 中 `mappings` 段可能缺失或使用了 SRG 名称而非 Mojang 名称，导致开发环境（`runClient`/`runData`）中 Mixin 注入失败。

**症状**：`InvalidAccessorException: No candidates were found matching f_xxx_` 或 `InvalidInjectionException: @Inject annotation could not find any targets matching 'm_xxx_'`

**解决方案**：修补第三方 jar 中的 refmap，将 `mappings` 段的条目修正为 Mojang 名称。生产环境不受影响（混淆后使用 `searge` 段的 SRG 名）。

### 空 Mixin 配置文件

即使模组自身不使用 Mixin，当前置模组（如 Curios、GeckoLib）触发了 Mixin 加载时，模组也需要提供一个空的 `{modid}.mixins.json`，并在 jar manifest 中声明 `MixinConfigs`。

### GeckoLib 示例物品栏

GeckoLib 在开发环境中会注册 "Geckolib Examples" 创造模式物品栏。生产环境自动关闭。开发环境可通过 JVM 属性 `geckolib.disable_examples=true` 关闭，已在 `build.gradle` 的 `configureEach` 中配置。

### 配方条件序列化器注册过晚

自定义 Forge 配方条件（`IConditionSerializer`）若在 `FMLCommonSetupEvent`（`commonSetup`）中 `CraftingHelper.register(...)`，`runData` 会在生成条件配方时报 `JsonSyntaxException: Unknown condition type: <id>`（datagen 序列化条件时序列化器尚未注册）。

**解决方案**：在 `@Mod` 主类**构造方法**中注册，早于 datagen 序列化。

### 食物效果与进食事件的先后顺序

`PasterDreamFoodItem.finishUsingItem` 内部先调用 `FoodData.eat`，再 `entity.addEffect(food 携带的效果)`；而 `LivingEntityUseItemEvent.Finish` 在 `finishUsingItem` 返回之后才触发。因此依赖「进食后已获得某效果」的逻辑（如料理溢出转黄心）在 `Finish` 阶段检查效果是可行的，且吃到授予该效果的那一口本身也会被计入；反之，若在 `Start` 阶段检查效果，则会漏掉第一口。

**结论**：判断「本次进食是否享受某进食生效的效果」应在 `Finish` 阶段检查效果，而非 `Start`。

### 结构内方块属性需经 mapping.json 的 block_properties 设置

搬运结构 NBT 时，某些方块在原作靠**自定义方块类**实现的行为，重制后若改用原版类就会丢失。典型：风泊树叶在原作是不腐烂的普通 `Block`，改用原版 `LeavesBlock` 后会随随机刻腐烂；而大型风泊树等结构又依赖树叶不腐烂。

**症状**：世界生成的大结构树叶随时间消失。

**解决方案**：在 `document/design/mapping.json` 的 `block_properties`（手动维护段，`generate_id_mapping` 重新生成时会保留）中，为对应**旧短名**强制写入属性，例如：

```json
"windmoor_leaves_0": { "persistent": "true" },
"windmoor_leaves_1": { "persistent": "true" }
```

再重跑 `convert_structure`，或直接修正已转换 NBT palette 中对应条目的属性。反过来，若希望方块恢复普通行为（会腐烂），则从 `block_properties` 移除该覆盖并修正 NBT。

### 删除/合并已登记方块 ID 需补兼容层并清理引用

搬运后若删除或合并某个方块 ID（如把 `pink_mushroom_pores` 并入 `pink_mushroom_block`），旧存档与已转换结构 NBT 仍会引用该 ID，导致方块丢失。

**解决方案**：
1. 在 Forge 总线（`MinecraftForge.EVENT_BUS`）监听 `MissingMappingsEvent`，把旧 ID `remap` 到新方块/物品，修复旧存档与背包数据。
2. 检查 `src/main/resources` 下结构 NBT 的 palette：结构模板不走注册表重映射，需直接修正 NBT，或更新 `mapping.json` 后重跑 `convert_structure`（属性可用 `block_properties` 覆盖）。
3. 同步清理注册、物品、创造栏、标签、战利品表、语言中对该 ID 的引用，并刷新 `ID映射表.md` 与 `mapping.json`。

### Capability Provider 返回类型必须与 Capability 泛型一致

`ICapabilityProvider.getCapability` 里用非受检的 `.cast()` 转换是合法的编译期写法，但**实际返回值类型**与 `Capability<T>` 的 `T` 不符时，消费方在 `ifPresent`/取值处会抛 `ClassCastException`，异常点离真正的错误代码很远，极难定位。

**典型**：研钵物品曾把 `FluidTank[]` 作为 `ForgeCapabilities.FLUID_HANDLER_ITEM`（应为 `IFluidHandlerItem`）返回。JEI 的 `GetAllFluidContainerCapability.getAllContainer()` 扫描全物品时命中并抛异常；因该扫描在 `registerRecipes` 最前面执行，`PluginCaller` 捕获异常后**整个 `pasterdream` JEI 插件本次注册全部中断**——研钵、梦之釜、陶盆等所有配方从 JEI 消失（症状是「JEI 里查不到某类配方」）。

**解决方案**：
1. Provider 返回的实例必须与 Capability 泛型匹配：`FLUID_HANDLER_ITEM` → `IFluidHandlerItem`，`ITEM_HANDLER` → `IItemHandler`。
2. 遍历第三方 Capability 时避免带类型的 `ifPresent`，改用 `Object o = stack.getCapability(cap).resolve().orElse(null); if (o instanceof X x) { ... }`，让单个坏 Provider 只被跳过，而不是拖垮整段逻辑。
3. 提醒：`IRecipeRegistration#registerRecipes` 是一个整体方法，任何一步抛异常都会中断**其后所有** `addRecipes`；易崩的扫描类逻辑应靠后放或自行兜底。
