# 战技冷却架构（状态效果为真值）—— 已回退

> 状态：**已回退**。该方案在本地开发过、**未提交**，经商议后回退，改用原版物品冷却架构。
> 本文件记录其设计思路、实现机制、缺点与回退原因，供未来参考；回退时一并删除了下列代码：
>
> - `world/effect/SkillCooldownEffect`、`world/effect/ProtectedTimedEffect`
> - `helper/cooldown/SkillCooldownWriteGuard`、`helper/cooldown/SkillCooldownDisplayEnforcer`
> - `mixin/ItemCooldownsMixin`、`mixin/ServerItemCooldownsMixin`、`mixin/ClientPacketListenerMixin`
> - `init/ModEffects` 的 `skill_cooldown` 注册及其语言条目

---

## 一、动机

原有战技冷却直接读写玩家物品栏的**原版物品冷却**（`player.getCooldowns()`）作为判定真值。问题：

1. 其它模组会给玩家物品栏内的物品施加原版冷却（典型：BOSS 攻击给全物品上无限/超长冷却），
   导致战技被外部逻辑「锁死」。
2. 直接清除又会与外部模组互相干扰，且客户端残留倒计时。

## 二、架构思路（效果真值）

把冷却的**真值**从原版物品冷却迁移到**受保护状态效果**，原版物品冷却降级为**纯视觉表现**：

```
SkillCooldownHelper.applySharedCooldown
        ├─→ SkillCooldownEffect (id: skill_cooldown)          ← 真值（受保护、隐藏图标、不可清除/拒绝）
        └─→ #pasterdream:skill_cooldown 标签物品的原版冷却     ← 仅视觉表现
```

判定统一走 `SkillCooldownHelper.isSkillOnCooldown(player)`（读效果），与物品栏原版冷却完全解耦。

### 机制与防护

| 环节 | 类 | 作用 |
|------|----|------|
| 真值 | `SkillCooldownEffect extends ProtectedTimedEffect` | 隐藏图标；不可被牛奶 / `/effect clear` / 其它 mod 清除，不可被 `MobEffectEvent.Applicable` 拒绝施加；提前解除需 `allowRemoval` 显式授权 |
| 入口 | `SkillCooldownHelper` | 施加 / 判定 / 清除 / 缩放；`tryStartSkill`「锁定 + 冷却」一步闸门 |
| 写入授权 | `SkillCooldownWriteGuard`（ThreadLocal） | 仅在授权范围内放行本模组对原版冷却的写入，兼容集成服务器双线程 |
| 双端拦截 | `mixin/ItemCooldownsMixin` | **客户端与服务端双侧**拦截外部对战技标签物品原版冷却的写入 / 清除（外部模组常在客户端本地预测里写冷却，仅拦服务端会残留）。本模组写入经 guard 放行 |
| 同步放行 | `mixin/ClientPacketListenerMixin` | 放行服务端→客户端的 `handleItemCooldown` |
| 直改 map 兜底 | `mixin/ServerItemCooldownsMixin` | 拦截绕过 `addCooldown`、直接 `getCooldowns().put(...)` + `onCooldownStarted` 的外部写法（如 RevelationFix 捆绑的阿波伦机制） |
| 每 tick 校正 | `SkillCooldownDisplayEnforcer`（PlayerTickEvent，双端） | 玩家不在共享冷却中时，清掉战技物品上任何残留的原版冷却 |
| 脚本接口 | KubeJS `PasterDreamSkills` | `startSharedCooldown` / `tryStartCooldown` / `isOnCooldown` / `isSkillLocked` / `clearSharedCooldown` / 倍率查询 |

## 三、缺点（回退原因）

### 核心：外部武器很难接入

外部模组的武器（如 Goety / EndingLibrary 等）**冷却逻辑写死在 Java 里、使用原版物品冷却**。
想让它们参与本模组的共享冷却，两条路都不可接受：

- **加进 `#pasterdream:skill_cooldown` 标签** → 其原版冷却的写入 / 清除立刻被
  `ItemCooldownsMixin` 与 `SkillCooldownDisplayEnforcer` 拦截 / 校正，导致外部武器**自身的冷却失效**
  （UI 与逻辑都不对）。
- **自己用 KubeJS 重写**整套冷却 → 等于放弃外部武器原有逻辑，成本极高且行为漂移。

反向的互锁（我方战技与外部武器共冷却）也只能靠脚本在外部武器侧叠加判定，**无法用标签统一表达**。

### 其它

- **复杂度高**：为「冷却显示」单独维护 3 个 mixin + guard + enforcer，跨客户端 / 服务端、集成服务器线程、
  `/reload`、标签运行时枚举等边界极多，容易漏（曾有客户端本地预测未拦导致的残留）。
- **语义分裂**：真值（效果）与显示（原版冷却）是两套状态，需时刻保持同步，为「显示正确」付出额外代价。
- **收益有限**：共享冷却本就是自模组武器之间的机制，原版物品冷却已能表达。

## 四、回退后的架构

冷却真值恢复为**原版物品冷却**：

- **施加**：`SkillCooldownHelper.applySharedCooldown(player, baseTicks)` —— 对
  `#pasterdream:skill_cooldown` 标签下所有物品写入原版冷却，时长按 `skill_cooldown_reduction` 缩减。
- **判定**：`player.getCooldowns().isOnCooldown(item)`；物品的 `use` / `useOn` 由原版
  `ServerPlayerGameMode` 自动按冷却拦截，无需在物品内重复判。
- 无 mixin、无保护效果、无每 tick 校正。

## 五、回退时保留的改动（BUG 修复）

以下改动与该架构无关，属独立缺陷修复，回退时已保留：

1. **非 `use` 路径补锁定判定**：`FluffyWindAlloyHoeItem.useOn`、`MurakumoKusanagiItem` 挥砍（`onSwing`）、
   `InfernoSwordItem.hurtEnemy` 补 `SkillLockHelper` 判定；高频路径用 `isSkillLockedSilent` 免刷屏。
2. **蓄势类战技再施放闸门**：`SharpMeltDreamSwordItem`（`SharpCharged`）、`ShadowSwordItem`
   （`nightmare_slash`）叠加「已蓄势」判断，避免未命中时反复右键重复扣资源 / 刷冷却。
3. **TerraBlade / 萦风雷矛接入共享冷却**：TerraBlade 的 5t 自身冷却改为共享；雷矛投掷冷却并入共享
   （不缩放，与虚影 200t 兜底严格对齐），虚影返回提前解除。为此 `SkillCooldownHelper` 保留了
   `applySharedCooldownExact`（不缩放）与 `clearSharedCooldown`（清除标签物品冷却）两个方法。

上述 1、2 已登记到 `程序规范文档.md` 的「易犯错误记录」。
