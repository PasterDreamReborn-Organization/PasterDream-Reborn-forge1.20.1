## 三、工作量估算

### 按难度分层

**Layer 1 — 简单方块（直接搬运，低工作量）**
- ShadowDungeonDoor1Block, Shadowdungeondoor3Block（纯被动方块，无逻辑）
- ShadowDungeonKey0Block, ShadowDungeonKey1Block（逻辑仅破坏+给物品）

**Layer 2 — 中等方块（含简单交互逻辑）**
- ShadowDungeonDoor0Block, Shadowdungeondoor2Block（3×3 填充/销毁 + 钥匙检查）
- ShadowBrazierBlock（GeckoLib 动画 + 战斗波次脚本）

**Layer 3 — 复杂系统（需要 GeckoLib + BlockEntity + 多 Procedure）**
- ShadowDungeonPortalBlock + 全部配套类（核心交互：出口/入口/生成地牢）
- BrokenShadowDungeonProtalBlock + 全部配套类（修复机制）

**Layer 4 — 世界生成**
- 结构定义 JSON 文件（3个）
- 结构 NBT 模板文件（20个）
- 生物群系关联（`biome_shadow_0` 已存在）

**Layer 5 — Procedure 重写**
- 9 个 MCreator Procedure → 重构为清晰的 Java 方法
- 最大的重写工作是 `ShadowDungeonPortalPr2Procedure`（地牢生成，涉及 20 个 NBT 模板的随机化 + 分层延迟放置）

### 建议搬运顺序

1. **资源先行**：先迁移所有 NBT 模板、Geo 模型、纹理、音效
2. **简单方块**：Door1/Door3/Key0/Key1
3. **门系统**：Door0/Door2 + DoorPr0/Pr1/Pr2 逻辑
4. **传送门系统**：PortalBlock/BrokenProtal + TileEntity + Procedure
5. **火盆**：BrazierBlock + 战斗 Procedure
6. **世界生成**：JSON 配置（等结构和方块就位后最后接入）
7. **成就进度**：TODO（暂不搬运）

## 四、特殊注意事项

### 4.1 TABITEM_1（调试物品）
原作使用 `TABITEM_1` 作为调试工具将传送门设为出口。新项目中该物品尚未搬运，可以考虑：
- 方案A：同样搬运一个调试物品
- 方案B：改用其他方式（如 command 或 creative only 交互）
- 方案C：暂时忽略，出口功能通过其他途径实现

### 4.2 Structure Block Processor
原作的 `shadow_dungeon.nbt` 包含 `minecraft:structure_block`，使用 `block_ignore` processor 在世界生成时跳过，然后这些 structure_block 被世界中原有的方块激活（`StructureBlock17Pr0Procedure` 由 tick 触发）。需要确认新项目中是否沿用此机制，还是改用 jigsaw 自动拼接。

### 4.3 依赖的成就（暂不搬运）
- `achievement_shadow_b_0` — 进入暗影地牢的前提成就（传送门激活时检查）
- `achievement_shadow_c_0` — 首次进入地牢时颁发
- `achievement_hide_14` — 修复传送门的前提成就
- `achievement_shadow_npc_5` — 打开最终门的前提成就

这些成就目前暂不搬运（TODO），需要在相关 Procedure 中暂时移除成就检查或使用临时条件替代。

### 4.4 CD 冷却存储
原作使用 BlockEntity 的 `persistentData` NBT 存储 CD 状态（`cd`/`time`/`exit`/`layer1~5`）。新项目应沿用 BlockEntity 的 `saveAdditional`/`load` 进行持久化。
