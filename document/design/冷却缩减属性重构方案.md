# 冷却缩减属性重构方案

> 状态：**已实现**
> 范围：`ModAttributes.BLINK_CD` / `ModAttributes.SKILL_COOLDOWN_RATE` 及其全部引用
> 目标：把「冷却倍率」改成语义为「冷却缩减」的属性，默认值 `0`，**正值 = 减少冷却**，方便饰品/效果以正值提供增益
> 已确认：重命名注册 ID；所有来源统一用 `ADDITION` 做**加法叠乘**；超过 100% 的部分直接截断；修饰器与文案统一为百分比；旧存档不迁移
> 实现要点：缩减属性默认 `0`、上限 `1.0`，`+100%` 缩减对应 0 冷却；`RangedAttribute` 会把超过 100% 的部分钳掉，冷却辅助类不再设置 25% 下限

---

## 一、为什么改

- 现有两个属性都是「倍率」：默认 `1.0`，越小越强。
- 饰品要减少冷却就必须给**负值**（如 `-0.05`），而属性显示通常按数值正负染色，负值会显示成红色，容易被玩家理解成负面效果。
- 改成「冷却缩减」后，默认 `0.0`，收益是**正值**（如 `+0.20` = 冷却 -20%），显示为绿色/蓝色；真正的惩罚才用负值，显示红色。
- 这不会改变底层“最终冷却时长”的算法，只改变**属性的语义、默认值、修饰器符号和叠乘方式**。

### 2.2 运行时公式

- 存在期间 `BlinkSkill.execute` 直接拦截（`BlinkSkill.java:27`）。

**战技**：`helper/cooldown/SkillCooldownHelper.java:27-29, 58-68`

```java
applySharedCooldown(player, baseTicks)
    -> applySharedCooldownTicks(player, scaleCooldown(player, baseTicks))

scaleCooldown = Math.max(1, Math.round(baseTicks * getSkillCooldownMultiplier(player)))
getSkillCooldownMultiplier = SKILL_COOLDOWN_RATE 属性值（默认 1.0）
```

- 对 `#pasterdream:skill_cooldown` 标签下所有物品写原版物品冷却。
- `applySharedCooldownExact`（`:37-39`）**故意不缩放**，用于萦风雷矛投掷虚影 200t 与冷却严格对齐；重构后必须继续保持“不缩放”。
- `clearSharedCooldown`（`:47-54`）只清原版物品冷却，与属性无关。

### 2.3 当前叠乘模型

`blink_cd` / `skill_cooldown_rate` 上的修饰器混用了 `ADDITION`、`MULTIPLY_TOTAL`、`MULTIPLY_BASE`：

- `ADDITION`：先把倍率加减（默认 1.0 上做加法）。
- `MULTIPLY_TOTAL`：在加法结果上乘 `(1 + amount)`。
- `MULTIPLY_BASE`：在加法结果上乘 `(1 + amount)`（对基础值生效，属性只有默认基础值，所以与 TOTAL 等价）。

这导致同一套“减 CD”效果在不同来源之间采用不同叠乘方式，数值不直观，也不利于统一成“缩减”。

## 四、调研发现的问题

1. **顺风效果符号写反（已确认是 BUG）**
   `TailwindEffect.java:44` 用 `+0.7 / +0.6 MULTIPLY_BASE`，实际把瞬身术冷却变成 `1.7× / 1.6×`，与类注释“降低闪烁冷却”以及 `风之旅途风向机制搬运分析.md:74` 写的“×0.7 / ×0.6”都矛盾。
   重构时改为**缩减**：amplifier 0 / 1 分别为 `+0.3 / +0.4`（等效 `0.7× / 0.6×`）。

2. **叠乘模型不统一（已确认统一为 `ADDITION`）**
   同样是“减 CD”，万象之戒用 `ADDITION`，盔甲/效果用 `MULTIPLY_TOTAL`，顺风/逆风用 `MULTIPLY_BASE`。重构后所有来源统一用 `ADDITION`：缩减百分比直接相加，超过 100% 的部分由属性上限截断。

3. **手写 tooltip 的单位不统一（已确认统一为百分比）**
   当前有 `-0.2 瞬身术冷却`、`-5%`、`+7 瞬身术冷却` 三种写法。改成缩减后统一为百分比：
   - 正面：`+20% 瞬身术冷却缩减`
   - 负面：`瞬身术冷却时间 +700%`（公爵币的 `-7` 缩减等价于 `8×` 冷却，直接写缩减值会非常反直觉）

4. **属性会随实体存档保存**
   `LivingEntity.addAdditionalSaveData` 会写入 `attributes`，`AttributeMap.load` 按注册 ID 恢复；找不到的 ID 会打日志并跳过（`Ignoring unknown attribute`）。
   因此：
   - **只改数值语义、不换注册 ID**：旧存档里的 `-0.05`、`+7` 会被当成“缩减值”解释，后果严重（负收益变正收益、公爵币从 `8×` 变成 `-700%` 缩减）。
   - **换注册 ID**：旧属性数据被安全忽略，但旧的永久修饰器（怒之灵药等）会丢失，需要重新获取。
   结论（已确认）：**必须换 ID**；**旧存档不做迁移**，接受开发期永久 buff 丢失。

5. **`applySharedCooldownExact` 不能被误改**
   萦风雷矛投掷要求冷却与虚影 200t 严格对齐，重构时只能改 `applySharedCooldown` 的缩放，不能给 `applySharedCooldownExact` 加缩放。

6. **瞬身术是“效果时长”而不是物品冷却**
   重构 `BLINK_CD` 时只影响 `BlinkSkill.applyCooldown` 传入的 `MobEffectInstance` 时长；不要顺手改成原版物品冷却，否则会与 `QymCloudBootsItem` 的解冷却逻辑、`BlinkCooldownEffect` 的拦截链路冲突。

7. **`RapidReactionEffect` 手动移除修饰器**
   它在 `removeAttributeModifiers` 里手动移除 `BLINK_CD` 的 UUID（`:23-24`）。属性重命名/改 UUID 时这里必须同步，否则效果结束会残留修饰器。

## 五、重构设计（推荐）

### 5.1 新属性

| 旧 | 新常量 | 新注册 ID | 默认值 | 范围 | 显示名 |
|---|---|---|---|---|---|
| `BLINK_CD` | `BLINK_COOLDOWN_REDUCTION` | `blink_cooldown_reduction` | `0.0` | `-10.0 ~ 1.0` | 瞬身术冷却缩减 |
| `SKILL_COOLDOWN_RATE` | `SKILL_COOLDOWN_REDUCTION` | `skill_cooldown_reduction` | `0.0` | `-10.0 ~ 1.0` | 战技冷却缩减 |

- 正值 = 减少冷却；`0.20` 表示 -20% 冷却。
- 负值 = 增加冷却；`-2.0` 表示冷却 `3×`。
- `ADDITION` 下 `getValue()` = 所有来源缩减值之和；`RangedAttribute` 的 `max = 1.0` 会把超过 100% 的部分直接截断（115% → 100%）。
- `min = -10.0` 只用于惩罚方向；最终倍率再由辅助类钳到 `0.0 ~ 10.0`。

### 5.2 公式与聚合

统一由一个工具方法把“缩减值”转成“冷却倍率”：

```java
private static final double MIN_COOLDOWN_FACTOR = 0.0;  // 允许 0 冷却
private static final double MAX_COOLDOWN_FACTOR = 10.0; // 惩罚最多 10 倍

public static double getCooldownFactor(Player player, Attribute attribute) {
    AttributeInstance instance = player.getAttribute(attribute);
    if (instance == null) return 1.0;

    double reduction = Mth.clamp(instance.getValue(), -10.0, 1.0);
    return Mth.clamp(1.0 - reduction, MIN_COOLDOWN_FACTOR, MAX_COOLDOWN_FACTOR);
}
```

- **瞬身术**：`duration = round(base * factor)`，`base` 仍为 50 / 100 tick（鞘翅）；`factor == 0` 时**不施加** `BlinkCooldownEffect`。
- **战技**：`ticks = round(baseTicks * factor)`；`factor == 0` 时**不写入**物品冷却。
- 不再使用 `Math.max(1, ...)`，否则 0 冷却会被强行变成 1 tick。

### 5.3 叠乘模型（统一 `ADDITION`，100% 封顶）

**所有来源统一使用 `ADDITION`**，缩减百分比直接相加：

```
总缩减 = clamp(Σ 缩减值ᵢ, -10.0, 1.0)
最终倍率 = clamp(1 - 总缩减, 0.0, 10.0)
```

- 每个修饰器的 `amount` 就是缩减比例：`+0.05` = -5%，`-7.0` = +700% 冷却。
- `+100%` 缩减 → `factor = 0`，实现真正的 0 冷却。
- 超过 100% 的部分不参与计算：`RangedAttribute` 的 `max = 1.0` 会把 115% 截成 100%，辅助类再 `clamp` 一次兜底。
- 代价：从旧版乘法叠乘改为加法叠乘，多来源同时存在时会更强。当前满配战技 `20% + 20% + 15% + 20% + 10% + 30% = 115%`，会直接到 0 冷却；需要按 5.5 的提示调整数值或接受这一强度。

**叠乘变化与平衡提示**

- 4 件盔甲 + 风势（战技）：
  - 旧：`0.95^4 × 0.8 ≈ 0.6516`（-34.8%）
  - 新：`1 - (0.20 + 0.20) = 0.60`（-40%）
- 4 件盔甲 + 风势 + 怒之灵药 + 燃起 + 振奋 + 狂暴（战技）：
  - 旧：`0.95^4 × 0.8 × 0.85 × 0.8 × 0.9 × 0.7 ≈ 0.2791`（-72.1%）
  - 新：总缩减 `0.20 + 0.20 + 0.15 + 0.20 + 0.10 + 0.30 = 1.15` → 截断为 `1.0` → `factor = 0`（0 冷却）
- 结论：加法叠乘比旧版更强，当前满配战技会直接到 0 冷却。如果不想让常规满配就归零，需要下调个别来源数值；如果这正是目标，则保持现值即可。

### 5.6 特殊说明

- **UUID 可保留**：属性换了，但同一来源的 UUID 仍可复用；只要同一属性内不重复即可。若担心旧存档残留，也可以换新 UUID。
- **不要保留旧注册 ID 作为别名**：两个属性同时存在会让玩家/脚本/存档出现两套冷却来源，收益叠加且难以排查。
- **KubeJS 返回值**：`getSkillCooldownReduction` 返回原始缩减值（默认 `0.0`）；内部 `SkillCooldownHelper.getSkillCooldownMultiplier` 继续返回转换后的最终倍率（默认 `1.0`），供 Java 侧使用。
- **属性显示**：`ADDITION` 下属性面板会显示正确总和；超过 100% 时被 `RangedAttribute` 的 `max = 1.0` 截断为 100%，与实际 0 冷却一致。
- **外部来源**：新增来源统一使用 `ADDITION`，正数 = 减 CD。不要再写 `MULTIPLY_TOTAL` / `MULTIPLY_BASE`。

## 六、存档与兼容性

1. 旧存档的 `attributes` 中会保留 `pasterdream:blink_cd` / `pasterdream:skill_cooldown_rate` 条目。
2. 重命名后 `AttributeMap.load` 找不到这两个 ID，会打印 `Ignoring unknown attribute ...` 并跳过；不会崩溃。
3. 旧条目上的永久修饰器（怒之灵药等）不会迁移到新属性，**已确认不做迁移**，开发期直接接受丢失。
